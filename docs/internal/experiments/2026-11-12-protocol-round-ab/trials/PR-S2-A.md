### 1.2 编排流程（三段式演算）

1. **draft**：PM 计划落独立板 `--board .expert-taskboards/order-export.json`（一个项目一个板，禁止混板），每子任务一条 `create --draft`，`--owner` 标意向专家、`--desc` 写验收标准、`--dep` 声明依赖、`--scope` 声明关联域（hook 第三查与 verify 依据；评审条目加 `--kind review`）。`todo_write` 同步里程碑给用户。**批准前零 spawn**（draft 不可 claim，工具级兜底）。
2. **approve**：用户在场由用户逐条核对（验收标准、依赖、范围）后 `approve`；依赖未满足的条目先回 pending，随依赖 done 自动提升 ready。未通过的保持 draft 重规划，确不推进的 `reject`。
3. **spawn**：仅 ready 后逐项召唤。召唤前必须用自有 `list_experts`（或读 `expert-sources/merged/roster.json`）核对花名册真实存在名——注意两套命名的坑（后端架构师≠后端工程师、安全审计专家≠安全工程师）；实施专家走 `summon_expert` 白纸召唤（persona 由工具注入，自动追加经验池尾部注入与末行 origin-chain 标记，编排者不手工捏造标记行）；任务书显式引用任务 id（形如 `T<数字>`）触发派工即回写 auto-claim。done 时核对实际执行者与 owner 一致。

## 三、并行/串行分析与写冲突、共享上下文考量

### 3.1 关键前提：前后端是否同一仓库/工作树

- **前后端分仓**（两个 cwd）：T2 与 T3 可**真并行**——互不共享工作树，写互斥不适用；用 `summon_experts` 批量（≤8、并发 4）或两次并行 summon，各自任务书引用各自任务 id 触发 auto-claim，各自产出落盘 + bus send，回复 ≤10 行摘要，编排者 `read --box coordinator` 整合。
- **前后端同仓（monorepo，本场景默认假设）**：按 §3 共享工作树写互斥纪律——**同一仓库同一时间只委派一个写型专家**，派发前查项目板与在途委派确认无其他写任务在途。因此即便 T2/T3 文件面不相交（后端模块目录 vs 前端页面目录），**写阶段也必须串行派发**（T1→T2→T3）：理由是并行写会让两份未提交改动混在同一 git 工作树里，diff 无法按任务分账，任何一方误触 git restore/checkout 都会污染对方（正是任务书红线所防）。可选开启 `DSH_EXPERT_CWD_LOCK=1` 获得工具级执法（第二个异名写型专家**当场拒绝而非排队**，报错含持有者与等待/取消/声明只读三条出路）；并用 `taskboard.py own` 登记工件归属做文件级门禁（冲突具名拒 `artifact_owned`，终态自动让位）。

### 3.2 必须串行推进的边及理由

1. **T1 → T2/T3（契约先行）**：前后端唯一的耦合点是接口契约这份共享上下文。不定稿就并行，双端只能按猜测实现，任一字段/文件名变更即双份返工，且这正是委派振荡告警针对的典型成因（A↔B 在方案分歧未收敛时来回横跳，达 3 次来回即告警）——正确做法是先收敛契约（单点只读文档），再分头实现。
2. **T2,T3 → T4（评审后置）**：评审对象是实现 diff/产出，必须等实现完成；评审者与实现者不同领域且**独立白纸召唤，绝不用 fork**——fork 会让评审者继承编排者上下文框定（含实现者结果汇报），独立性优先于任何缓存收益（§3 召唤方式）。评审走 `--kind review` 状态机：pass 才收口；needs_revision 必带 findings、自动生成 repair、下游依赖自动改挂最新 repair；回炉人工上限 2 轮、超限转 escalated 交用户 `retry`。
3. **T4 → 交付/commit**：门禁强制顺序——里程碑完成、即将交付/commit 前必过门禁（大型任务独立评审 + PM 检查点均必过；PM 检查点默认向「项目推进专员」汇报进度/偏差/评审结论）。commit 前三查：未显式 `--install-hook` 时 hook 不触碰 `.git/hooks/`，交付说明须注明“门禁 hook 未开启，commit 前检查为模型自觉执行”。
4. **同仓时 T2 → T3 写串行**：见 3.1 写互斥。

### 3.3 可并行推进的面

- 分仓时 T2‖T3（契约 done 后同时派发）。
- 编排者的只读核验（读 diff、跑测试、grep 核对、端到端跑通核对）可与在途写任务并行——只读操作免委派、不占写互斥。
- 任务板自身的依赖自动提升（依赖 done → 下游 pending→ready）与在途任务无锁竞争（板写入 flock+CAS 串行化，写命令可带 `--expected-revision` CAS）。

### 3.4 共享上下文与协作配套

- **指针式材料引用**：契约文档对 T2/T3 都是材料——任务书只给“路径 + 读取指令”让专家自读，编排者不预读转述（防失真、省 token）；契约文档本身在 T2/T3 的要求段被列为只读保护对象（禁止改）。
- **专家间接力**：若 T3 联调阶段需要 T2 的实现细节，走 bus——T2 `send` 到 T3 信箱、T3 任务书只写 `read` 指令，编排者不过手转述。
- **并行协作纪律**：并行专家任务书必带“产出落盘 + bus send coordinator + 回复 ≤10 行摘要”（T2 任务书已组入）；完成汇报 subject 以 `[交付]` 开头仅限终态（防中途汇报被 watchdog 误 adopt）；长任务每阶段落 `progress` 检查点（断点续跑的进度清单正来源于此）。
- **失败与收口**：专家失败不回滚 claim——按板处置（换人 `reassign`/废弃 `fail`/崩溃 `recover`）；done 时核对实际执行者=owner；全部子任务收口后跑 `metrics` 反哺 routing.md，提炼 ≤3 条新教训入经验池（项目池 `.expert-lessons.md` + 专家池 `expert-lessons/<slug>.md`，重复已知教训不写），最后 `archive` 归档项目板、todo 清零不留 in_progress。
