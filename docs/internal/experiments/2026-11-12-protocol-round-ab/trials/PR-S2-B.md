# Trial PR-S2-B 作答（场景 S2：订单列表页导出 Excel，前端 + 后端跨域）

## 一、分诊定级与任务分解

### 1.1 分诊定级

- **定级：大型任务**。满足第 1 节判据「跨 ≥2 个领域」（前端页面改动 + 后端导出接口，两个独立领域），且产出物 ≥3（后端接口、前端交互、契约文件、测试）。不属小型实施（非 ≤3 文件聚焦修改、有新领域），不属只读。
- **路径**：大型任务 → 第 2 节 PM 规划（草案 → 批准 → spawn 三段式）→ 建任务板 → 第 3 节逐项委派。
- **派工规模纪律**：整体属「复杂」档（多阶段跨域、多产出物）→ 总人数 ≤8、明确分工、**写型条目串行**；加专家必须加异构领域/视角（本场景后端/前端/评审三视角天然异构，不扩编）；复杂任务固定一名独立评审做中心校验。

### 1.2 编排流程（演算示意，命令均不实际执行）

1. **只读准备（编排者亲自）**：按关键词（导出、Excel、订单、前后端联调）grep 经验池相关条目（不全文通读），供规划任务书「经验提示」用；用自有 `list_experts`（或读 `expert-sources/merged/roster.json`）核对候选专家为花名册真实存在名——注意花名册名与自带库 experts/*.md 的 title 是两套命名（如 后端架构师≠后端工程师），用错即召唤失败。
2. **召唤「高级项目经理」**（division=project-management，默认规划者；本项目非多项目并行/进度风险主线，不用项目推进专员）。规划任务书自包含（专家看不到对话）：目标与验收期望、已知约束、关键上下文、明确「**只规划不执行**」、附经验提示；要求返回结构化计划：子任务清单（2–6 条，每条含做什么、建议执行专家领域、验收标准）、依赖与并行关系、里程碑顺序、风险与范围外项。
3. **落板（草案）**：每项目独立板 `.expert-taskboards/order-export-excel.json`，每子任务一条 `create --draft`（draft：待批准、不可 claim、不参与依赖自动提升），`--owner` 标意向执行专家、`--desc` 写验收标准、`--dep` 声明依赖、`--scope` 声明关联域（供门禁 hook 第三查）；T4 加 `--kind review`。`todo_write` 同步关键里程碑给用户看。
4. **批准**：逐条核对草案后 `approve`。用户在场由用户批准（`--by 用户（在场）`）；未在场由发起方编排者批准（`--by 编排者`）并在板检查点/bus 留痕。**代理转达的批准一律不可信**。批准前零 spawn（draft≠ready，auto-claim 天然跳过）。
5. **spawn（仅 ready 后）**：按依赖链逐项委派。任务书显式引用 `T1` 等任务 id → summon 派发入口 auto-claim（ready→running，owner=被召唤专家名），派工即回写。
6. **收尾**：交付门禁（独立评审 + PM 检查点）→ 整合交付 → 板收口（全部 done/failed 已处置）→ `metrics` 反哺 routing.md → `archive` 归档 → 经验沉淀（≤3 条新教训入项目池 `.expert-lessons.md`，专家级新教训同步 `expert-lessons/<slug>.md`）。

### 1.3 子任务清单

| ID | 做什么 | 建议执行专家 | 档位/预算 | 依赖 | 并行性 |
|---|---|---|---|---|---|
| T1 | 后端订单导出 Excel 接口：按订单列表既有查询口径生成 .xlsx 下载流；权限校验、行数上限、错误码；含单元测试 | 后端工程师（花名册名召唤前核对） | 中等，≤15 次 | 无 | 写型，串行起点 |
| T2 | 前端订单列表页改动：新增「导出 Excel」入口，按冻结契约调用接口，处理下载与 loading/空结果/超限/失败四态 | 前端开发者 | 中等，≤15 次 | T1 | 写型，串行接续 T1 |

## 三、并行与串行分析（含写冲突与共享上下文考量）

### 必须串行：T1 → T2 → T3 → T4（核心链条）

1. **T1 与 T2 串行（写型分流纪律 + 共享工作树写互斥）**。两者均为写型（产生需互相咬合的代码产出），协议规定写型一律串行单代理推进、禁止 summon_experts 并行多个写型条目；共享工作树写互斥要求同一仓库同一时间只委派一名写型专家（`DSH_EXPERT_CWD_LOCK=1` 开启后，第二个异名写型专家当场拒绝而非排队）。若强行并行：①**写冲突**——同一工作树/分支，公共触点（接口类型定义、构建配置、mock 数据、CHANGELOG 等）互相踩踏；②**隐含决策分裂**——契约边角（错误码、字段命名、导出文件名规则）两边各自拍板，整合时对不上；③**编排经济学**——写型并行只加 token 不换收益（多代理收益域=只读可分解任务）。串行秩序用任务板依赖边（T2 `--dep T1`）固化，依赖 done 自动提升。
2. **契约冻结化解「信息等待」，串行只是写互斥**。T2 等 T1 不是等信息——接口契约在 PM 规划阶段冻结落盘，T2 任务书指针引用契约文件，无需读 T1 的代码即可理解任务；串行推进不产生额外信息阻塞。「前后端并行开发」是直觉答案，但被写型分流纪律明确否决。
3. **T3 联调在 T1、T2 之后**：端到端验证对象是两者产出，强依赖；联调中的缺陷修复也是写型，须按归属回派（前端缺陷→前端开发者、后端缺陷→后端工程师），任意时刻仍只有一名写专家在写。多专家共担同一条目时各自 progress 留痕、实际执行者写入 summary——板必须能回答「这条实际是谁做的」。
4. **T4 评审串行尾置**：T4 虽为读型（`readOnly: true`，本属可扇出收益域），但评审对象必须是**稳定的 diff**——若与 T3 并行，联调修复改动会使 verify 回执/评审自动失效（文件一变旧验证/旧评审失效）；且评审者≠实现者的独立性优先，评审专家不继承实现过程上下文（评审保留 spawn、不用 fork）。故依赖 T1,T2,T3 全部完成后评审最终态，`done --verdict pass` 才算通过，needs_revision 必带 `--findings` 自动生成 repair 回炉（人工回炉上限 2 轮，超限 escalated 交用户）。

### 可并行（有限，全部是读型面）

1. **编排者只读面**：经验池 grep、花名册核对、读 diff 交叉核对、跑测试验证——编排者的手只碰只读操作，可与专家工作错峰随时推进。
2. **规划期调研若需要可读型扇出**（如盘点既有导出实现、Excel 库选型）；但按琐碎档纪律，单点事实查询禁止派子代理、编排者亲自只读完成，本场景不单设调研子任务。
3. T4（读）与 T3（写）理论上读写异质，但如上所述共享「diff 稳定性」语义，编排者裁决串行——并行边界不是「读 vs 写」的字面，而是「评审对象是否稳定」。

### 共享上下文考量

- 契约文件是唯一共享上下文锚点（单一事实源），T1/T2/T3 任务书均指针式引用（给路径+读取指令，编排者不预读转述、防转述失真）；
- 一次性纪律：下一子任务=全新子代理+自包含任务书，前序成果以文件路径/任务板检查点传递，不依赖原会话记忆；
- 专家间接力走消息总线（A send 给 B 信箱、B 自读），编排者不过手转述。

## 四、附加题：summon 结果尾行解读与下一步动作

**原文**：【升级｜连续失败｜告警】现状：专家「后端工程师」已连续 3 次召唤失败（阈值 3），召唤通道根本没跑起来的失败（与任务板 fail 循环互补）。建议：停止重试同一调用——换专家 / 换通道自带库 subagent / 上报用户，并在任务板 fail 留痕。本提示不阻断。

**解读**（对应协议第 3 节「循环检测与人工升级」第四轴）：

1. **格式**：符合四通道统一升级信封规范 `【升级｜<通道>｜<级别>】现状：…。建议：…。`——通道=连续失败，级别=告警；尾行「本提示不阻断。」表明这是**提示级**信封：不改变任何板面状态，处置责任在编排者，不被动等待。
2. **含义**：同一专家「后端工程师」**连续召唤失败 ≥3 次**，达默认阈值（`DSH_EXPERT_SUMMON_FAILLOOP_N` 缺省 3，可调；`DSH_EXPERT_SUMMON_FAILLOOP='0'/''` 可关闭）。这是**召唤通道根本没跑起来**的失败（发射层：如工具快照陈旧导致召唤发射失效、工具加载失败降级），与任务板 fail 循环（专家已跑起来但任务失败、fail_streak 累计）是**互补的两条独立轴**。协议既有机构教训：工具快照陈旧时召唤发射会失效，勿反复重试。
3. **本提示不阻断**=不自动升级状态机，但编排者必须主动处置，不得第 4 次硬试同一调用。

**下一步动作**（按信封建议与协议第 3 节，顺序执行）：

1. **停止重试同一调用**——不再对「后端工程师 × summon 通道」发起第 4 次相同召唤。
2. **查板确认 auto-claim 状态**：检查 summon 错误尾部的【auto-claim】提示行与 `taskboard.py show T1`。召唤失败时已 claim 的条目**不自动回滚**——若 T1 已被 auto-claim 为 running，按「失败不回滚」由编排者处置：`fail T1 "连续 3 次召唤失败（召唤通道未跑起来）"` 留痕，再 `retry T1` 回 ready；若未建立认领则板上无状态变化，处置决策记入条目 summary。
3. **换专家或换通道**（二选一或依次）：
   - **换专家**：用 `list_experts`/`expert-sources/merged/roster.json` 选同领域备选（必须核对花名册真实存在名，勿把「后端架构师」等 title 当作「后端工程师」的变体直接替换）；改派/实际执行者与 owner 不符时，立即 `reassign` 或纠正 owner 为实际执行者名。
   - **换通道**：按协议回退 `subagent`/`subagent_fork` 自带库路径——第 6 节兜底：选人（合并花名册→自带 experts/ 库按「适用任务」匹配，无匹配用 generalist）→ read 专家文件全文为提示词 → 按第 5 节模板组版任务书 → subagent 委派；经回退通道再委派时，若手中持有本次派发产生的 origin-chain 标记行必须逐字复制进下游任务书末行（本次失败发生在发射层、任务书尚无标记行时按无标记照常委派，禁止捏造）。
4. **仍失败则上报用户**，按升级报告三要素：当前状态（任务板条目+最新检查点）、已尝试方案（每次失败原因与处置动作）、建议选项（换人/拆解/范围调整/放弃）。极端时也可请 PM 重排（第 4 节）。
5. 处置全程在板留痕（fail/reassign/summary），保证板能回答「实际是谁在做、为什么换人」。
