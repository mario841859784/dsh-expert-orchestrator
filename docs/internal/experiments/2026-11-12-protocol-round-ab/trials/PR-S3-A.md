## 一、处置动作序列（工具命令级）

### 第 0 步｜只读核实（写前先读）

```bash
python3 <技能目录>/tools/taskboard.py show T7
python3 <技能目录>/tools/taskboard.py status
```

- `show T7`：读检查点轨迹，核对三次 fail 原因原文与次数；同时执行 §3.2 规则 3 的探针（escalated 记录次数，预期 0）；记末行 `revision=N` 备 CAS。
- `status`：盘点板面，确认无其他 running、无「已升级待用户处置」行。**不跑 `boards` 总览**（非开新板/收口场景）。

```bash
# 编排者只读手（协议明文允许：跑测试核对、grep 核对）
grep -n "<依赖声明/CI 配置/环境变量注入点 关键词>" <相关配置路径>
# 经验池关键词检索（不全文通读）
grep -n "<构建失败/依赖安装/环境变量/超时 关键词>" .expert-lessons.md
grep -n "<同上关键词>" <技能目录>/lessons.md
```

目的：判定三因是否同一根因（预期均指向环境预置缺失），并取经验池相关条目作任务书「经验提示」。

### 第 1 步｜五锚自检（触发条件已满足：连续 2 轮无实质进展）

- 锚1：子任务=T7 修复构建失败；上一步=第 3 次 fail 已记录。
- 锚2：同形第 4 次重派不推进总体目标。
- 锚3：连续 ≥2 轮无实质进展 → **强制换策略或召 PM 重排**（本场景两者都做：先过门禁 PM 检查点，再按调整计划换域重派）。
- 锚4：下一步是委派（PM 检查点 → DevOps 重派），编排者不亲自改。
- 锚5：上下文尚可，但要求专家产出落盘消息总线、只回 ≤10 行摘要。

### 第 2 步｜门禁：PM 检查点（"子任务验收不通过"触发门禁；大型任务必过）

```
# summon_expert（项目推进专员）——同步等结果（短串行步，下一步立即依赖其返回）
```

任务书要点（自包含，明确"只汇报与规划、不执行"）：T7 目标与三次失败原因**原文**（附证据）、板面状态、与原计划的偏差；要求返回：调整后的计划、风险处置、需用户决策事项。（任务书中 T7 处于 failed 非 ready，auto-claim 天然跳过，无误伤。）

### 第 3 步｜按 PM 调整计划更新板面与 todo

```bash
python3 <技能目录>/tools/taskboard.py retry T7 --expected-revision <第0步读到的revision>   # failed→ready，准备换域重派
# 若 PM 计划要求新增前置子任务（如「环境预置」）：taskboard.py create 落条目（按三段式则以 --draft 落板、发起方批准 approve 并在板留痕）
# 依赖变化用 set_dependencies（自带环检测）
```

todo_write 同步关键里程碑（T7 受阻 → 换域重派）给用户看。

### 第 4 步｜换域重派（强制换策略 = 换专家 + 换域）

```
# list_experts（或读 expert-sources/merged/roster.json）核对「DevOps 自动化工程师」的花名册真实名
# summon_expert（DevOps 自动化工程师，任务书显式引用 T7 → 派发入口 auto-claim：ready→running、owner=该专家）
```

任务书按 §5 模板组版，要点：
- 固定段五行（核实/红线/产出落盘/署名/persona）逐字复制，占位符按当次召唤解析；
- 检查点段**必填**（长任务/多阶段）：每完成一阶段 `progress` 落盘并 bus 同步 coordinator；无法产出阶段产出时至少 `heartbeat` 报活；
- 目标：修复构建失败，验收=构建成功；
- 上下文：工作目录、T7、三次失败原因**原文**（专家看不到对话，必须自带）、只读诊断已确认事实、相关文件路径（指针式引用让专家自读，编排者不预读转述）；
- 经验提示：第 0 步 grep 所得条目；
- 要求：先诊断后动手；逐项核实三因是否同一根因（若为环境预置缺失，先补齐预置再构建）；装依赖/注入环境变量/超时参数等环境操作属你域；完成汇报 subject 以 `[交付]` 开头（仅终态汇报发送）；
- 交付：修复说明 + 改动文件清单 + 构建成功日志路径；
- 完成定义（可机器验证）：以项目实际构建命令执行、退出码 0 且日志无 error 级输出。

兜底：花名册无该领域 → 按 §6 转自带 `experts/` 库以 `subagent` 委派；summon 结果尾部 auto-claim 提示跳过 → 手工 `python3 <技能目录>/tools/taskboard.py claim T7 <专家名>` 补齐。（可选代际加固：编排者生成 attempt_id，先 `claim T7 <专家名> --attempt <attempt_id>` 再 summon，attempt_id 随任务书下发——此时 auto-claim 因 owner 已有跳过属预期。）

### 第 5 步｜等待与监督

- summon 同步等结果，或后台委派后等完成通知回交——**禁止 sleep/定时轮询**；
- **不在 summon 等待期内对 T7 并行 reclaim**；如需长时间监督，按需显式跑：

```bash
python3 <技能目录>/tools/taskboard.py watchdog --bus-root <cwd>/.expert-bus
```

### 第 6 步｜完成后收尾

```bash
python3 <技能目录>/tools/taskboard.py done T7 "构建修复成功，构建命令退出码0" --rework 2 --switched
# --rework/--switched 按实际返工与换人次数记档，供 metrics 聚合回写 routing.md
python3 <技能目录>/tools/taskboard.py verify T7 <改动文件...>   # 验证回执；交付/commit 前门禁将再次触发（hook 分级执法）
```

- 核对实际执行者与 owner 一致，不一致立即纠正；
- 若出现经验池没有的新教训（如"构建失败三连因异 ⇒ 先诊断环境域再派工"），收尾提炼 ≤3 条入池（重复已知教训不写）；
- 全部子任务收口后任务板不留 in_progress。

### 预案｜换域重派后再失败（第 4 次失败）

不再第 5 次重试：`fail T7 "<第4次原因>"` 记录后**上报用户决策**——换策略与 PM 重排两个非重试分支均已耗尽，继续派工即违反"不要反复硬试"；上报附全部证据与已尝试清单，或按用户裁决废弃该任务。

### 禁止事项（本场景红线）

1. 禁止同形第 4 次重派（反复硬试同一调用）；
2. 禁止编排者亲自改代码/改配置/改环境修构建（实施写入禁令，只读手）；
3. 禁止跳过门禁 PM 检查点直接重派（大型任务必过）；
4. 禁止把 T7 误判为 escalated 而套用 §3.2 限额规则或强行上报（fail/retry ≠ escalated）；
5. 禁止在 summon 等待期内 reclaim T7、禁止 sleep/轮询等待。

## 二、是否上报用户

**本节点默认不上报，但设有三个即时上报触发器。**

不上报的依据（逐条核对协议的强制上报触发器，均未命中）：
- §3.2 规则 3 的 escalation 上限只针对**进入 escalated 状态**的任务——T7 走的是 fail→retry（failed↔ready），从未进入 escalated，限额（缺省 1）未达到，探针已核实；
- §4.1 "回炉上限 2 轮，仍不过→上报用户决策"针对评审 verdict 循环，本场景非 review kind 任务；
- repair 重试上限转 escalated 属 review kind 工具机制，同样不适用；
- 无规约实质冲突。

协议对实施失败循环的既定处置是"换专家重试、改用自带库、或请 PM 重排"——用户是终局裁决面，不是每次失败的上报对象。

即时上报触发器（满足任一即上报）：
- (a) 只读诊断或 PM 检查点显示根因在编排者/PM 权限之外（凭据/CI secrets、环境变量注入策略、预算配额等需用户裁决事项）；
- (b) PM 检查点返回「需用户决策事项」；
- (c) 换域重派后再失败（第 4 次失败）。

上报内容要点（若触发）：
1. T7 目标与现态（failed，已 3+ 次失败，附三次失败原因原文）；
2. 只读诊断结论与证据（三因是否同根因、指向环境预置缺失的依据）；
3. 已采取的处置与结果（PM 检查点结论、换域重派情况）；
4. 需用户裁决的具体选项（提供凭据 / 调整环境变量注入方式 / 放宽构建超时 / 废弃任务改道）；
5. 影响面（里程碑偏差、依赖 T7 的下游条目被阻塞）。
