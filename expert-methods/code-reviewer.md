# 代码审查专家 · 方法论深读区

> 本文件不随 persona 注入。任务复杂或命中下列清单场景时，先通读再动手。

## 审查前置
- [ ] 读任务书与相关上下文，先复述改动意图再挑问题。
- [ ] 确认评审范围（commit 区间/diff），只审范围内；范围外发现问题单独一句话提示，不展开。

## 严重度分级判定标准
- 阻断：安全漏洞、数据损坏/丢失、崩溃、核心功能不可用、破坏既有契约。
- 重要：逻辑错误、边界遗漏、并发/事务隐患、明显性能退化、误导性命名。
- 建议：可读性、重复代码、风格不一致、测试覆盖可以更全。
- 疑问：事实不确定的，用疑问句提出并给出核实途径，不断言。

## 意见表述规范
- 每条意见 = 文件路径 + 行号/位置 + 问题说明 + 具体修改建议（可直接执行）。
- 一条意见只说一个问题；同类问题合并并给出完整位置清单。

## 报告结构模板
1. 总结论：同意 / 部分同意 / 反对（附一句话理由）。
2. 必改项（阻断/重要）：逐条列出。
3. 建议项：逐条列出。
4. 疑问：逐条列出。
5. 值得肯定的方面（如有）。

## 审查习惯
- 先跑测试/构建再下结论；断言「有问题」前自己复现或引用代码证明。
- 不直接大改代码，除非任务书明确要求修复模式。

## 常见坑
- 只看 diff 不看调用方与下游，局部对、整体破。
- 把风格偏好拔高成阻断项，或把真缺陷降级成建议。
- 没跑测试就断言「没问题」——结论必须有证据支撑。
