# 运维工程师 · 方法论深读区

> 本文件不随 persona 注入。任务复杂或命中下列清单场景时，先通读再动手。

## 动手前核对清单
- [ ] 环境拓扑：目标机器、服务单元、端口、依赖服务与运行方式（systemd/容器/进程管理器）。
- [ ] 配置来源：哪些是包内静态、哪些是运行时用户数据、哪些在环境变量或密钥管理。
- [ ] 当前状态留痕：改动前记录版本号/状态输出，作为回滚基线。

## 变更操作核对
- [ ] 影响面声明：本次改动影响哪些服务/用户/数据。
- [ ] 破坏性操作（删除、重启、覆盖配置）：逐项对照任务书授权范围，超范围即停并上报。
- [ ] 变更最小化：不做顺手升级、不顺手修无关配置。

## 发布步骤核对清单
1. 构建/拉取 → 核对产物版本与预期一致。
2. 部署 → 确认文件落位、权限/属主保持。
3. 启动/重载 → 看启动日志关键行（如 preset ready）与进程 PID。
4. 健康检查 → 服务 active、无重启循环、核心功能冒烟。
5. 留痕 → 终态版本、时间、验证证据写入交付报告。

## 回滚前置条件
- [ ] 有可直接执行的回滚步骤（含上一版本号/镜像/配置备份）。
- [ ] 明确回滚触发标准（报错关键字、健康检查失败判定）。
- [ ] 数据类操作先备份；无法回滚的操作必须事先上报确认，不得先斩后奏。

## 排查证据链
日志（报错关键字 + 时间点）→ 状态（服务/进程/磁盘/网络）→ 最小复现 → 定位假设 → 验证假设。每一步留证据，不跳步下结论。

## 常见坑
- 改了 A 副本而运行时实际加载的是 B 路径——动配置前先核实真实加载来源。
- 重启/覆盖后权限与属主变化导致下一轮部署或服务异常。
- 只验证「起来了」没验证「功能对」——健康检查之后必须补功能冒烟。
